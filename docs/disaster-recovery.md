# Backup and disaster recovery

Scope: loss of a region, or loss of data. Losing a single broker or a single zone is already covered by the 3-broker, 3-zone cluster (see the
"Kafka broker down" runbook); this document does not repeat that.

## How much each kind of data matters

| Data | Lives in | If lost | Protection |
|---|---|---|---|
| Orders, trips, ratings, outbox | Postgres (order, trip, rating) | **Truly lost**: it is the source of truth | Postgres backups + PITR (below) |
| Business events (`order.*`, `trip.*`) | Kafka, retained 7 days | Committed data can be rebuilt from Postgres; a consumer more than 7 days behind loses events | MirrorMaker 2 to the standby region; S3 archive |
| Driver location, driver status, leases | Redis (one master + replica, monitored by Sentinel) | **Self-healing**: drivers report again every few seconds; when a lease expires the driver can receive orders again | No backup needed |
| Avro schemas | Schema Registry (Kafka topic `_schemas`) | New producers/consumers cannot decode messages | Lives in Kafka: replicated by MirrorMaker 2 if `_schemas` is added to `topicsPattern`; or re-register from `services/pkg/events/schemas/` (services register themselves on startup) |

RPO/RTO per layer, separating what has been **measured** from **targets** (adjust to your actual contracts):

| Layer | RPO (maximum data loss) | RTO (recovery time) | Status |
|---|---|---|---|
| Redis losing 1 node | 0 to ~1 second of the last writes (AOF `everysec`, asynchronous replication) | Failover: **measured at 4 to 5 s** with `down-after` 3 s (the manifest uses 5 s, so expect ~6 to 8 s); planned (`preStop`): ~12 s | Measured on real Redis/Sentinel on a dev machine, **not on a real cluster** |
| Postgres, `pg_dump` CronJob only (this repo) | **Up to 6 hours** + job run time (each backup is a point-in-time snapshot, no PITR) | Unknown for real data. Local drill: 0 to 1 s, but the DB is only ~8 KB per service (see below), so **this figure says nothing about production** | Run end to end on a real Postgres on a dev machine; **not on a real cluster, not to a real S3** |
| Managed Postgres + PITR (recommended) | A few seconds (WAL) | Depends on the provider and the size | Not in the repo; needs to be configured |
| Kafka to the standby region | A few tens of seconds (expected; MirrorMaker 2 is asynchronous) | A few tens of minutes, mostly the manual steps in section 4 | Target, not measured |

## 0. Redis: Sentinel (losing a node, not a region)

Redis needs no backup (see the table above) but it does need to be **available**: when the master dies, Matching and Driver Location Service stop. Every service uses
`pkg/redisconn`: `REDIS_SENTINEL_ADDRS` (ConfigMap `grab-mini-config`, the list of Sentinels) and `REDIS_MASTER_NAME` make the client ask Sentinel for
the current master and **follow failovers by itself**, without restarting the service. Passwords come through `REDIS_PASSWORD_FILE` and `REDIS_SENTINEL_PASSWORD_FILE`
(the same `grab-mini-redis` Secret, key `password`, which you create).

**Redis deployment manifests** (`deploy/k8s/base/redis/`, generated by `generate.py`, scripts in `deploy/redis/`): a 3-pod StatefulSet, each pod being `redis`
+ `sentinel` + `redis_exporter` (quorum 2/3); a 5Gi PVC per pod, AOF `everysec`, `noeviction`; anti-affinity requiring different nodes and topologySpread requiring different zones;
a PDB allowing 1 pod to be down; probes, requests/limits, pinned image versions; password from a Secret; a PodMonitor and 2 alerts (`RedisNotExactlyOneMaster`, `RedisMemoryNearLimit`).
Which pod is master is decided by Sentinel at runtime, not fixed by ordinal: a restarted pod asks Sentinel and joins as a replica of the current master.
To use a managed Redis instead: remove `redis/` from the kustomization, leave `REDIS_SENTINEL_ADDRS` empty, and set `REDIS_ADDR`.

Verified with `scripts/test-redis-ha.sh` (real Redis 7.4 and Sentinel in Docker, each "pod" being two containers sharing a network namespace, running exactly the scripts the ConfigMap carries): first
startup (redis-0 is master, 2 replicas, the 3 Sentinels see each other, `CKQUORUM` OK, Sentinel returns **hostnames**, not IPs); the password is enforced (NOAUTH); writes replicate; **killing the whole of pod 0**, Sentinel
elects a new master within 4 to 5 s without losing keys; when pod 0 comes back it **becomes a replica** of the new master and catches up; no "ghost" Sentinels are left behind (fixed ids); `preStop` hands the master role over; and
`TestTheClientFollowsAFailover` (the real Go client, `pkg/redisconn`) runs against this set of 3 Sentinels and passes. **Not verified**, because there is no cluster: real scheduling/anti-affinity/zones, PVCs, DNS of the headless
Service, probes run by the kubelet, NetworkPolicy, and behaviour when a whole zone is lost. NetworkPolicy: the default policy denies ingress to every `part-of=grab-mini` pod, including Redis; the allow rules Redis needs
(services to 6379/26379, between Redis pods, Prometheus to the exporter on 9121) are now in place in `deploy/k8s/base/network/` (generated by `generate.py`, checked by `check.py`), but are untested on a real CNI.

Sentinel adds availability, not capacity: there is still a single master. Replicas replicate asynchronously, so a failover can lose the last few seconds of writes
(location heals itself; but a lease or a `match:<orderId>` written last may also be lost, and the consequences of that, for example an order being matched twice, are **untested**).

## 1. Postgres

Use a managed service (RDS/Cloud SQL/…) with **automated backups + PITR + a read replica in another region** enabled, or an operator (CloudNativePG, Crunchy) with
`barman`/`pgBackRest` shipping WAL to S3: only those give PITR (an RPO of a few seconds). This repo provides a **second layer of insurance**, not a replacement:

**Logical backup** (`deploy/k8s/base/backup/`, `scripts/pg-backup.sh`): CronJobs `backup-order-service`, `backup-trip-service`, `backup-rating-service`, every 6 hours.
An init container (`postgres:16-alpine`) runs `pg_dump -Fc` into an emptyDir and then checks the archive is readable (`pg_restore --list`); the main container (`amazon/aws-cli`, version pinned)
pushes it to `BACKUP_TARGET/<service>/<service>-<UTC>.dump`. The name carries a UTC timestamp, so "latest" is a sort by name. Configuration: `BACKUP_TARGET`, `BACKUP_S3_ENDPOINT` (non-AWS S3),
`AWS_DEFAULT_REGION` in the `grab-mini-data-ops` ConfigMap; credentials in the `grab-mini-backup` Secret (`AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY`), which you create. The default value of `BACKUP_TARGET`
is `s3://CHANGE-ME-...` so the job **fails loudly** rather than quietly writing somewhere. The job only writes, never deletes: deleting old backups is the bucket's lifecycle rule. Limitations:
each dump is a snapshot (one transaction), so the RPO is up to 6 hours plus the job's run time; `pg_dump` reads the whole DB, so point it at a read replica if the DB is large; if the three services share one database, the
same content is dumped three times; `pg_dump` must be the same as or newer than the server's major version (currently `postgres:16`); there is no client-side encryption (it relies on bucket-side encryption); nobody checks
the contents apart from the drill.

**Restore drill** (`scripts/pg-restore-drill.sh`, procedure in the [runbook](runbook.md#backup-and-restore)): fetches the latest backup, restores it into a scratch DB, checks
the schema version (`schema_migrations_<service>` must equal the latest migration in the code, with no half-applied migration), that the tables exist, and that the main table is not empty; prints row counts, size and timing; cleans up after itself.
**Mandatory every quarter.** A backup that has never been test-restored is not a backup.

**Actually run** (`scripts/test-data-ops.sh`, real Postgres 16 in Docker, the three services' real migrations): two dumps are created, the drill picks the **newer** one
(5 orders, not 6), the schema is at version 7/8/2 as in the code, row counts match the live DB, the scratch DB is dropped; the drill **fails** exactly when the schema version is wrong, rows are missing, or there is no backup
(and still cleans up); and the S3 path exactly as the CronJob runs it (dump with the postgres image, upload with the `amazon/aws-cli` image to an S3-compatible server, the drill downloads and restores).
The measured restore time is **0 to 1 second**, but on ~8 KB of data per dump: it only proves the procedure is correct, **it is not the production RTO**.
To get a real RTO: run the drill on a full-size backup, record the time (download + `pg_restore`; usually bounded by bandwidth and index builds) and add the manual steps (stopping writes, changing the Secret, bringing services back, reconciling).
**Not verified:** the CronJob running on a real cluster (kubelet, Secrets, NetworkPolicy egress to Postgres and S3, emptyDir quota), real AWS S3, and the drill at production size.

**Data cleanup:**
- Dedupe rows: the two older CronJobs in `deploy/k8s/base/retention/` delete `processed_events` (trip) and `rating_events` (rating) older than 30 days in batches of 10,000. 30 days is the lower bound:
  Kafka keeps 7 days and a DLQ may wait for someone to handle it; below that, a late redrive could be processed twice.
- **Orders and trips** (new): `retention-order-orders` (order-service's `orders` table) and `retention-trip-trips` (trip-service's `trips` and `cancelled_orders`), daily at 03:43,
  in batches of 5,000, `scripts/pg-retention.sh`. Deletes **finished** rows older than `RETENTION_DAYS` (default **180**, the script refuses < 30): `CANCELLED`/`NO_DRIVER` orders; `COMPLETED`/`CANCELLED` trips
  (age taken from `completed_at`/`cancelled_at`, falling back to `created_at`); `cancelled_orders` markers. `MATCHED` is the last order state order-service knows (it is not told when the trip finishes), so such orders are only deleted when older than
  `MATCHED_ORDER_DAYS` (default **365**, when no trip can still be running). It **never** touches `PENDING`, `ASSIGNED`/`IN_PROGRESS` trips, `outbox` (cleaned up on publish),
  `outbox_dead` (left for a human), or `driver_reviews` (review history, not pruned). There are no foreign keys between these tables (services refer to each other by TEXT id, one DB per service), so the only ordering to preserve is time: every
  threshold is ≥ 30 days. A consequence to be aware of: trips older than 180 days can no longer be rated (the score already lives in rating-service); **deletion is data loss in the live DB**, so the long-term record is the backup (set the bucket lifecycle
  to match legal requirements); there is no separate archive store. Run against a real Postgres with 12,009 orders and 8 trips covering every state/age (see `scripts/test-data-ops.sh`): exactly the right rows were deleted (12,003 orders over 3 batches, 4 trips, 1 marker),
  every unfinished row was left intact, a second run deleted 0, dry-run only counted, and unsafe settings were refused. Limitation: there is no index on `created_at`, so each batch scans the table; that is fine for a daily job, and
  an index (a new migration) should be added if the tables reach tens of millions of rows.

## 2. Kafka to the standby region (`deploy/k8s/dr/mirrormaker2.yaml`)

Apply it in the cluster of the **standby region**. It replicates `order.*` and `trip.*` (not `driver.location.*`: telemetry), keeps topic names unchanged
(`IdentityReplicationPolicy`) so consumers do not have to change configuration, and syncs consumer group offsets (`sync.group.offsets`).

Limitations to be aware of:

- Asynchronous: if the primary region dies, events not yet replicated are lost (RPO > 0). Postgres is the source of truth to reconcile against.
- Offsets are translated **approximately**, so consumers may reprocess a few messages just before the cutover point. The consumers are already idempotent (eventId,
  `match:<orderId>`); this is exactly why they need to be idempotent.
- There is no measurement of replication lag yet, and the manifest has only had its schema validated; it has **not yet been run on a real cluster**.

## 3. Cold archive on S3 (`deploy/k8s/dr/s3-archive.yaml`)

The Kafka Connect S3 sink writes the business topics to S3 as Avro, partitioned by hour. It is independent of both Kafka clusters and is meant for auditing and rebuilding
read models. It has also not yet been run on a real cluster; the S3 sink plugin is under the Confluent Community License.

## 4. Failover procedure

Only when the primary region will not recover soon. Each step should be rehearsed beforehand:

1. **Decide and announce.** Failing over has a cost (some unreplicated events are lost, offsets are approximate): it is decided by someone with the authority to do so.
2. **Stop writes in the primary region if it is still reachable** (scale to 0), to avoid both regions accepting orders.
3. **Postgres**: promote the replica in the standby region (or restore from PITR to the most recent point). Record the timestamp.
4. **Kafka**: check how far MirrorMaker 2 has caught up (the connector's `kafka_consumer_lag`, or compare end offsets); stop MirrorMaker 2.
5. **Schema Registry**: make sure all schemas are present (the `_schemas` topic was replicated, or re-register them).
6. **Redis**: bring up a fresh, empty instance. Drivers will report their locations again on their own; for the first few seconds Matching may return `NO_DRIVER`.
7. **Start the services** in the standby region (`kubectl apply -k deploy/k8s/base`, replace `DATABASE_URL`, set the Kafka bootstrap through the ConfigMap). Run
   `migrate` first.
8. **Switch DNS/gateway** to the standby region.
9. **Once stable**: reconcile the orders in Postgres against the Kafka events; `PENDING` orders that are too old need handling by hand (cancel or re-match). Run `dlq-redrive`
   if any dead letters appeared.

Returning to the primary region (failback) is a failover in the opposite direction: do it calmly, follow the steps above in reverse, and make sure the data in the two
regions has not diverged.

## Not done yet

- No **region failover** drill has been run yet, and no restore drill on a real cluster or with production-sized data. The only measurements: the Postgres restore and the Redis failover on a dev machine (see the table at the top); every other RPO/RTO is a target.
- There is no automated monthly restore check yet (the drill is run by hand from a machine with access; a CronJob would need its own scratch Postgres).
- Postgres backups have no client-side encryption, no protection against deletion (that needs a bucket with object lock/versioning, which you configure), and no PITR.
- Redis has no backup (on purpose); Redis Cluster cannot be used (see docs/performance.md).
- Multi-region active-active: not done. Two regions both writing to Postgres and both matching drivers needs its own conflict design.
